Deploy Dataroma holdings crawler + minimal holdings UI

1. Scope

Two parts, same session:

  1. Deploy/try: run DataromaSpider against the live site (local docker-compose), limited to 5 investors first, PIPELINE_MODE=holdings so HoldingPipeline upserts into Postgres.
  2. UI: one new page /holdings — flat table of investor + ticker + shares + value + quarter + activity, backed by one new API endpoint. No drill-down.

2. Data flow

flowchart LR A[DataromaSpider live crawl] -->|HoldingItem| B[HoldingPipeline] B -->|upsert| C[(Postgres: investors, companies, holdings)] D[GET /holdings/] --> C E[HoldingsPage.tsx] --> D

3. Crawl limit mechanism

New env var DATAROMA_INVESTOR_LIMIT, read in parse_home, same style as existing IDEA_LINKS_LIMIT in IdeaSpider. Default 0 = no limit (full 83). Set to 5 for this run.

4. API endpoint

New file api/routes/holdings.py, same shape as companies.py:

GET /holdings/?skip=0&limit=100
-> list of { investor_name, ticker, company_name, quarter_date, shares, value_usd, pct_portfolio, activity }

Join Holding + Investor + Company. Requires adding Investor/Holding to api/models/__init__.py (currently missing) and a HoldingResponse Pydantic schema.

5. Frontend

New frontend/src/pages/HoldingsPage.tsx, route /holdings added to App.tsx + nav link in Layout.tsx. Plain HTML table, no charts, no filters — matches "keep it really really simple". Fetches /holdings/ via existing axios client pattern (see CompaniesPage.tsx).

6. Module design blocks

Module: DataromaSpider investor-limit slicing

  • Responsibility: cap how many investors get crawled per run via env var.
  • Interface: reads DATAROMA_INVESTOR_LIMIT in parse_home, slices investor list before yielding requests.
  • Dependencies: none new.
  • Size target: +5 lines to existing spider.

Module: api/routes/holdings.py

  • Responsibility: read-only endpoint returning joined holding rows.
  • Interface: GET /holdings/ — query params skip/limit, returns List[HoldingResponse].
  • Dependencies: api.database.get_db, api.models.Investor/Holding/Company, api.schemas.HoldingResponse.
  • Size target: ~30 lines, mirrors companies.py.

Module: frontend/src/pages/HoldingsPage.tsx

  • Responsibility: render holdings table.
  • Interface: no props, fetches on mount, renders <table>.
  • Dependencies: axios client, existing loading/error pattern from CompaniesPage.tsx.
  • Size target: under 100 lines.

7. Error handling

Crawl: existing ban-aware throttle + retry settings apply unchanged (already wired for IdeaSpider, shared settings.py). If probe_dataroma.sh fails pre-crawl, abort before hitting live site. API: standard FastAPI validation, empty list if no data yet (not a 404 — matches companies/users endpoints).

8. Testing

test_scope: true. New: api/tests/test_holdings_api.py (endpoint returns joined rows, empty-list case). Playwright DOM check on /holdings page after frontend build — table renders with expected row count once seeded.

9. Out of scope (explicitly)

  • No GitHub Actions / weekly_ingest.yml wiring this pass.
  • No investor detail page, no filters/search, no charts.
  • No full 83-investor crawl this pass — 5 only, to verify live pipeline first.
