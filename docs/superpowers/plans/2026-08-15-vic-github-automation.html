How the GitHub Actions piece will work

Not yet implemented — this page explains the design; nothing below has been written to .github/workflows/ yet. Execution happens after /clear.

What already exists

.github/workflows/weekly_ingest.yml already runs on a cron schedule (Mondays 03:00 UTC) plus manual workflow_dispatch. It spins up a Postgres service container and calls scripts/weekly_refresh.sh. This doesn't need a webhook — GitHub's own scheduler triggers it; no external hook required.

The gap: backfilling 13,925 ideas doesn't fit a weekly cron

At ~10-12s/request, the full backlog takes ~38-40 hours. GitHub Actions caps a single job at 6 hours (hosted runners) — one run can't finish it. That's exactly why backfill_ideas.sh is checkpointed: each run does one batch (default 500 links, ~1.5-2h) and stops.

Proposed automation flow

GitHub Actions
scheduled cron (e.g. every 6h)
→
checkout repo
+ spin up Postgres service
→
scripts/backfill_ideas.sh
one batch, reads/writes checkpoint
→
commit updated
data/backfill_checkpoint.json
back to the branch

Once offset == total in the checkpoint, the backfill workflow is effectively done (later runs are instant no-ops), and weekly_ingest.yml takes over permanently for incremental updates only (already changed to RESET_DB=0 in the plan).

Concrete steps (for the fresh session to implement)

1. New workflow file .github/workflows/vic_backfill.yml — same Postgres-service pattern as weekly_ingest.yml, but on a tighter schedule (e.g. 0 */6 * * *), calling scripts/backfill_ideas.sh instead of weekly_refresh.sh.
2. Because each GH Actions run is a fresh checkout, the checkpoint file must be committed back after each batch — add a step: git config a bot identity, git add data/backfill_checkpoint.json, commit + push if changed. This is the one piece needing a repo-write permission (contents: write in the workflow's permissions: block) — a real "outbound action," so this step gets flagged for your explicit approval before the workflow is enabled, per this session's standing rule on pushes/writes.
3. VIC_USERNAME/VIC_PASSWORD go into GitHub repo secrets (Settings → Secrets → Actions), referenced as ${{ secrets.VIC_USERNAME }} — never in the workflow file itself.
4. Postgres data itself: since GH Actions Postgres service containers are ephemeral per-run, the scraped rows only persist if the workflow also exports/pushes them somewhere durable (e.g. a DB dump artifact, or pointing DATABASE_URL at your real persistent DB instead of the ephemeral CI one). Worth deciding before enabling: does backfill write to a real hosted Postgres, or to CI's throwaway one? — flagging this now since it changes the workflow's DB connection config.
5. Optional: a Slack/Discord webhook step reporting batch progress (offset/total) — deferred unless you want it; not required for the core loop to work.

Why no proxy/anti-detection setup is in this flow

Same finding as before: the site isn't blocking requests. GitHub Actions runners use rotating cloud IPs (Azure ranges) which is a separate consideration from bans — if VIC ever rate-limits CI IPs specifically, BanAwareThrottleMiddleware will surface it in the logs (backoff/abort), and that's the point to reassess, not before.
